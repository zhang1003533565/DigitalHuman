# 旅游分析手动快照设计

## 背景

`/admin/travel-analytics` 当前从旅游分析明细表现场计算五项聚合指标，并使用 60 秒进程内缓存。明细新增、编辑、删除、Excel 导入或统计权限配置变化后，缓存会自动失效；管理页面还会在数据变更成功后重新加载指标摘要。

第一阶段需要改为持久化快照和管理员手动刷新：原始记录的修改不得自动改变后台指标、模型测试或游客统计问答结果。只有管理员主动生成并成功发布新快照后，所有统计消费者才统一切换到新结果。

## 目标与边界

### 目标

- 用数据库快照替代现场聚合与短时进程内缓存作为统计读取来源。
- 管理员通过明确操作原子生成五项指标的完整快照。
- 后台摘要、模型测试和游客统计问答统一读取最新成功快照。
- 原始数据变化后保留旧快照，并明确提示当前快照已落后。
- 尚无快照时不隐式计算；后台显示空状态，游客统计问答不可用。

### 非目标

- 第一阶段不增加定时刷新任务。
- 不提供快照历史管理、回滚或删除界面。
- 不改变原始旅游记录的实时增删改查和 Excel 导入能力。
- 不引入新的第三方依赖或数据库专用物化视图。

## 方案选择

采用“快照批次 + 指标快照明细”方案。每次刷新创建一个批次，并在同一事务中写入五项指标的 ADMIN 与 PUBLIC 结果。只有完整批次可以成为新的读取版本。

未采用每项指标独立覆盖，因为刷新中途失败可能产生指标版本不一致。未采用数据库物化视图，因为它增加数据库耦合，也不自然承载操作人、批次状态和失败隔离等审计语义。

## 数据模型

### `travel_analytics_snapshot_batch`

| 字段 | 含义 |
| --- | --- |
| `id` | 快照批次主键 |
| `status` | `BUILDING`、`READY` 或 `FAILED` |
| `source_record_count` | 生成时的原始记录总数 |
| `source_max_updated_at` | 生成时原始记录的最大更新时间；无记录时为空 |
| `source_data_version` | 生成时的原始数据版本号 |
| `metric_config_version` | 生成时影响指标输出的配置版本号 |
| `created_by` | 发起刷新的管理员标识 |
| `created_at` | 批次创建时间 |
| `completed_at` | 成功或失败结束时间 |

### `travel_analytics_metric_snapshot`

| 字段 | 含义 |
| --- | --- |
| `id` | 指标快照主键 |
| `batch_id` | 所属快照批次 |
| `scope` | `ADMIN` 或 `PUBLIC` |
| `metric` | 五项白名单指标之一 |
| `total_samples` | 原始样本总数 |
| `valid_samples` | 指标有效样本数 |
| `as_of` | 快照统计截至时间 |
| `items_json` | 聚合条目 JSON；不包含游客明细或标识 |
| `methodology` | 统计口径说明 |
| `warning` | 样本不足或空数据提示 |

`batch_id + scope + metric` 设置唯一约束。一个 `READY` 批次必须包含五项 ADMIN 结果和五项 PUBLIC 结果，共十条指标快照。旧批次保留用于追溯，但第一阶段的业务读取只使用最新 `READY` 批次。

### `travel_analytics_source_state`

该表保存一行统计来源状态：

| 字段 | 含义 |
| --- | --- |
| `id` | 固定状态行主键 |
| `data_version` | 每次原始记录新增、编辑、删除或成功导入后递增 |
| `metric_config_version` | 影响 PUBLIC 聚合输出的配置变化后递增 |
| `updated_at` | 来源状态最后更新时间 |

版本号更新必须与对应原始数据或配置写入处于同一事务。快照是否过期只比较版本号；记录数与最大更新时间用于页面展示和审计，不承担完整的变化检测职责。

## 服务边界

### 快照生成服务

快照生成服务是唯一允许现场聚合原始记录的入口。管理员发起刷新后，服务执行以下步骤：

1. 拒绝同一时刻的第二个刷新请求。
2. 在事务中读取一致的原始记录集合及来源水位。
3. 使用现有、可独立测试的指标计算逻辑生成 ADMIN 与 PUBLIC 两套结果。
4. 写入批次和十条指标快照。
5. 校验指标集合完整且无重复后，将批次发布为 `READY`。
6. 返回新批次元数据，由前端重新读取摘要。

批次先以 `BUILDING` 状态创建。指标计算与十条指标快照写入在单个事务中完成，完整性校验通过后才切换为 `READY`。若计算或写入失败，指标事务回滚，并在独立的失败记录步骤中将该批次标记为 `FAILED`、写入结束时间和脱敏错误摘要。`FAILED` 批次永不参与业务读取，最新成功批次继续提供服务。

### 快照查询服务

快照查询服务只读取最新 `READY` 批次，不回退到原始记录现场计算。后台摘要、后台模型测试和游客统计问答必须复用该服务，防止不同消费者看到不同版本。

没有成功快照时：

- 后台返回明确的“暂无快照”状态，而不是伪造零值统计。
- 游客统计接口返回不可用状态；聊天链路给出稳定的“统计数据尚未发布”提示。
- 管理员模型测试不可执行，并说明需要先生成快照。

### 来源变化检测

原始数据新增、编辑、删除或导入后不刷新、不清除快照。页面通过比较来源状态的 `data_version` 与快照批次的 `source_data_version` 判断数据是否变化。不得仅依赖记录数、最大更新时间或前端本地状态判断快照新旧。

统计权限配置的修改不会生成快照。由于 PUBLIC 快照结果受最小样本量影响，该配置变化时递增 `metric_config_version`，使当前快照显示为需要刷新；游客开放开关只控制访问权限，不递增版本，也不改变快照内容。

## API 设计

保留现有按指标读取接口，但其数据来源改为快照查询服务。新增管理员专用接口：

- `GET /api/admin/travel-analytics/snapshot`：返回最新成功批次元数据、来源是否变化及五项 ADMIN 摘要的可用状态。
- `POST /api/admin/travel-analytics/snapshot/refresh`：生成并发布完整新快照。

刷新接口只允许 ADMIN 调用。Observer 可以读取快照及变化状态，但不能发起刷新。普通游客只能经现有白名单指标接口读取 PUBLIC 快照，不得访问批次内部信息或管理员结果。

响应应区分以下状态：

- `NOT_CREATED`：从未成功生成快照。
- `READY`：快照可用且来源未变化。
- `STALE`：快照可用，但来源数据或影响指标的配置已变化。
- `REFRESHING`：已有刷新正在进行。

## 管理页面

原始记录列表继续实时加载。指标区域将当前含混的“刷新摘要”拆成两个动作：

- “重新加载快照”：只重新读取当前已发布快照，ADMIN 与 Observer 均可执行。
- “生成最新快照”：重新聚合并发布新批次，仅 ADMIN 可执行。

指标区域展示快照生成时间、操作人、来源记录数、当前状态和“游客问答仍使用此快照”的说明。来源变化时持续展示提醒，但不自动触发生成。尚无快照时展示引导空状态。

新增、编辑、删除和导入成功后，仅刷新原始记录列表与来源变化状态，不再调用指标面板的自动刷新或触发统计重算。保存 AI 权限配置也不会生成新快照。

## 并发与错误处理

- 同一时刻只允许一个快照刷新任务。刷新服务使用数据库级互斥锁覆盖多实例场景，并设置短等待上限；并发请求返回明确冲突响应，不排队隐式执行。
- 刷新按钮在请求期间显示进行中状态，防止重复提交。
- 刷新失败时保留并继续展示最新成功快照，同时显示可操作的失败原因。
- 写入不完整、指标重复或缺少任一 scope/metric 组合的批次不得标记为 `READY`。
- 快照 JSON 反序列化失败属于服务端数据完整性错误，不得回退读取原始明细。
- 快照中不得保存游客 ID、昵称、单条轨迹、单条消费或其他个人明细。

## 测试策略

### 后端

- 无快照时后台和游客接口返回约定的不可用状态，且不查询原始记录进行隐式计算。
- 管理员手动刷新原子生成一个批次和十条指标快照。
- 快照指标集合完整性和唯一约束生效。
- 原始数据修改后旧快照仍可读取，并报告 `STALE`。
- 第二次成功刷新后，所有消费者统一读取新批次。
- 刷新失败或并发刷新不会污染最新成功快照。
- ADMIN 可以刷新，Observer 和普通游客不能刷新。
- ADMIN 与 PUBLIC 快照继续遵守现有白名单、隐私和最小样本量规则。
- PUBLIC 配置变化正确触发来源过期判断，但不会自动生成快照。

### 前端

- 覆盖首次无快照空状态、可用状态和过期提示。
- 覆盖“重新加载快照”与“生成最新快照”的不同请求契约。
- 覆盖 ADMIN、Observer 的按钮权限和加载状态。
- 覆盖刷新失败后旧快照仍可见及错误提示。
- 覆盖原始记录变更后不自动生成快照，只更新过期状态。

### 回归验证

- 后端执行旅游分析服务、控制器、安全边界与数据库迁移相关测试。
- 管理端执行对应 Node 合同测试、ESLint 和生产构建。
- 验证游客聊天统计问答只读取最新 PUBLIC 快照。

## 验收标准

- 原始记录发生变化后，在管理员手动刷新前，后台指标、模型测试和游客问答结果保持不变。
- 一次成功刷新后，五项指标及 ADMIN/PUBLIC 两个作用域原子切换到同一批次。
- 系统首次无快照时不执行隐式聚合，并向后台和游客提供明确状态。
- 页面能够准确说明快照时间、来源变化和手动刷新结果。
- 任意失败、并发或权限异常都不会暴露原始游客数据或破坏最新成功快照。
