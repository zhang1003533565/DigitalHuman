# 景点正式主数据与内容绑定设计

## 目标

以 `ScenicFacility` 作为地图、游客端和后台管理唯一正式点位；结构化 DOCX 数据只负责导入、匹配和字段级应用。景点文化资料、游客呈现配置与口播版本均通过 `facilityId` 关联正式点位，避免两套景点身份。

## 数据边界

### 正式点位 `scenic_facilities`

保存列表、地图、搜索高频字段：`spotCode`、名称、分类、短简介、位置说明、经纬度、开放时间、封面、图集和地图可见性。`spotCode` 在未删除数据中唯一，是导入匹配的首选业务键。

### 结构化详情 `scenic_facility_details`

与正式点位一对一，按独立列保存建筑景观参数、核心功能、文化内涵、详细介绍、游玩亮点、演艺开放信息、游客须知和备注；不使用通用 JSON 或单一大文本代替业务字段。

### 游客呈现 `scenic_facility_presentation`

与正式点位一对一，保存语音开关、绑定口播、直播开关、默认体验和视频/流/摄像头来源。启用语音必须绑定已发布且音频有效的口播；启用直播必须存在对应来源。

### 导入暂存 `scenic_spot_structured_record`

保留 DOCX 原始字段，增加 `matchedFacilityId`、匹配状态、应用状态和最近应用时间。导入记录可处于未匹配、建议匹配、已匹配、已应用状态；一条记录最多绑定一个正式点位。

## 匹配与应用

匹配优先级为：已有 `matchedFacilityId`、`spotCode == spot_id`、规范化名称完全一致、名称相似候选。只有编码唯一匹配可自动建议，所有应用动作必须由管理员确认。

应用前返回逐字段差异。管理员可选择“仅填空字段”“逐字段选择”或“覆盖全部”，其中经纬度、分类、封面默认不参与覆盖。应用时保存正式点位、详情和呈现配置快照；回滚产生新历史记录，不删除来源。

## 页面

`/admin/spots/facilities` 是正式管理入口。设施列表增加资料状态与“内容配置”，编辑抽屉分为基础信息、文化资料、口播语音和直播配置。非景点设施仍可维护基础点位，但默认不展示文化、口播和直播入口。

`/admin/scenic-structured` 改为“景点资料导入”，只承担导入、校验、匹配、差异预览、应用与查看来源；移除游客呈现配置。

## 兼容迁移

已有结构化记录先按编码或唯一名称生成匹配建议，不静默覆盖正式点位。已有口播保留 `spotId` 兼容字段，同时新增 `facilityId`；完成绑定后所有新操作以 `facilityId` 为准。原结构化记录上的游客呈现配置在首次成功匹配时迁移到正式点位呈现表。

## 验证

- 后端测试覆盖独立字段持久化、匹配优先级、仅填空与选择覆盖、应用快照、呈现校验及口播归属校验。
- 前端契约测试覆盖设施内容配置、导入记录匹配、字段差异选择和结构化页面移除呈现配置。
- 完整运行 Maven 测试、前端契约测试、lint 和生产构建。
