# 景区数字人全系统升级设计

## 1. 目标

在保留现有 `frontend-visitor`、`frontend-admin`、`backend-java` 和 `ai-service` 四端架构的前提下，完成一轮覆盖产品体验、比赛展示、平台运营、移动端适配、工程质量和安全性的系统升级。

升级后的系统必须形成一条可真实使用、可稳定演示、可持续运营的主闭环：

```text
游客描述需求 → AI 规划路线 → 地图呈现与导航 → 数字人沿途讲解
→ 保存会话与行程 → 游客反馈 → 管理后台分析并优化内容
```

本轮不更换主要技术栈，不引入新的大型框架，不重写已经可用的数字人、知识库或地图模块。

## 2. 产品设计

### 2.1 游客端

游客端以行程任务为主线，减少页面之间相互独立的感觉。

1. 首页使用后台配置的 Banner、推荐景点、推荐路线、公告和游览提示，移除与接口数据重复的硬编码展示。
2. 首页提供快捷行程规划入口，收集游玩时间、同行人、兴趣和体力要求。
3. AI 导览回答除文本和语音外，还返回相关景点、路线、快捷追问、知识来源和地图入口。
4. 数字人明确展示加载、待机、聆听、思考、回答、失败和重试状态。
5. 路线推荐把兴趣、时长、强度、同行人等条件传给后端，由后端统一计算结果。
6. 地图、路线、景点与数字人页面通过路由参数或会话状态共享当前路线和景点上下文。
7. 历史记录支持查看并恢复对话或行程；反馈必须关联具体会话、消息或路线。
8. 所有数据页面提供加载、空数据、局部失败和重试状态。

### 2.2 管理端

管理端从数据录入工具升级为运营控制台。

1. 新增运营总览，展示游客量、会话量、问答成功率、知识命中率、满意度、热门问题、热门路线和服务健康状态。
2. 首页配置支持预览、排序、启停和跳转目标校验。
3. 知识库展示上传、解析、构建、可用和失败状态，并提供失败原因、召回测试与质量检查。
4. 模型配置移除 mock 保存和测试行为，统一供应商、模型、能力、启停与默认模型管理。
5. 景点、路线、设施和讲解词建立明确关联，避免重复录入和孤立数据。
6. 游客反馈增加待处理、处理中、已解决状态，以及分类、备注和筛选。
7. 配置修改与关键管理操作写入审计日志。

## 3. 移动端与响应式设计

### 3.1 游客端手机优先

游客端以 `360px` 宽度为最低主要适配基线，并覆盖常见手机、平板和桌面宽度。

- 手机端使用底部主导航或紧凑顶部导航，保证首页、AI 导览、路线、地图和个人中心可单手访问。
- 数字人页面在手机端改为上下分区：数字人舞台在上，对话与输入区在下；输入栏固定在安全区域上方。
- 地图筛选改为横向滚动快捷项或底部抽屉，景点详情使用底部卡片，避免遮挡地图。
- 路线详情采用纵向时间轴，主要操作固定在底部。
- 卡片、表格型信息、弹窗和按钮满足触控尺寸；处理刘海屏与底部安全区域。
- 禁止依赖鼠标悬停才能触发的核心操作。
- 图片使用响应式尺寸和延迟加载；长内容避免横向溢出。

### 3.2 管理端窄屏可用

管理后台以桌面为主要场景，同时保证平板和窄屏可操作。

- 侧边栏在窄屏折叠为抽屉。
- 数据表在窄屏保留关键列，其余列通过详情抽屉查看。
- 表单从多列切换为单列，操作按钮保持可见。
- 图表根据容器自动缩放，并为关键指标提供文本摘要。

### 3.3 响应式验收宽度

至少检查 `360px`、`390px`、`768px`、`1024px` 和 `1440px`。页面不得出现非预期横向滚动、操作遮挡、文本重叠或无法关闭的弹层。

## 4. 服务架构与数据流

### 4.1 行程规划

游客端提交规划条件到 Java 后端。Java 后端读取正式路线与景点数据，调用 AI 服务生成个性化推荐理由和提醒，再返回结构化结果。AI 服务不可用时，后端仍使用规则和官方路线模板返回可用结果。

结构化结果至少包含路线标识、景点顺序、预计时长、强度、推荐理由、提醒、坐标和关联设施。

### 4.2 数字人问答

问答流程为：

```text
问题输入 → 意图识别 → Agent 路由 → 知识检索 → 结构化回答
→ 流式文本 → 分段 TTS → Live2D 口型与动作 → 会话持久化
```

回答模型至少包含 `answer`、`spots`、`routes`、`suggestions`、`sources` 和请求追踪标识。前端可渐进展示文本，不等待全部语音生成完成。

### 4.3 运营分析

会话、消息、路线推荐、点击行为和反馈使用可关联标识形成数据链。管理端只展示后端聚合后的指标，不在前端从明细数据临时推算核心指标。

## 5. 错误处理与安全

- 四端使用一致的错误分类：参数错误、未认证、无权限、资源不存在、上游超时、AI 不可用和系统错误。
- AI 调用配置超时、有限重试和规则降级，避免用户停留在无限加载状态。
- 前端错误提示提供明确的恢复动作，不直接暴露内部异常或堆栈。
- 请求携带追踪标识，Java 后端与 AI 服务日志可以关联同一次操作。
- 高德地图密钥和安全密钥不得硬编码在提交的游客端源码中，改由环境配置注入，并限制可用域名；需要保密的服务密钥只保存在服务端。
- 模型 API Key 不返回明文，后台只能覆盖更新或显示掩码。
- 管理操作执行鉴权、参数校验和审计记录。

## 6. 代码边界

- 游客端建立共享 API 类型、加载/空状态/错误状态组件和响应式设计变量。
- 管理端复用现有 Ant Design 与 ECharts，不增加第二套组件库。
- Java 后端负责业务编排、权限、持久化、降级和聚合指标。
- AI 服务只负责模型能力、Agent 编排、RAG 与 TTS，不承载景区业务真值。
- 大型页面在修改涉及区域时拆出职责单一的组件或 Hook，但不进行无关的全仓重构。

## 7. 实施顺序

1. 记录当前构建与测试基线，补充关键回归测试。
2. 建立共享类型、响应式变量和通用状态组件。
3. 完成游客端行程规划、数字人结构化结果、页面联动与移动端改造。
4. 完成管理端运营总览、知识库状态、模型真实操作和窄屏适配。
5. 补齐 Java 后端的规划、结构化问答、反馈关联、指标聚合和错误协议。
6. 完善 AI 服务的结构化输出、超时、降级和追踪。
7. 清理 mock、硬编码、无效入口和敏感配置。
8. 完成各端验证与关键用户流程检查。

## 8. 测试与验收

### 8.1 自动验证

- 游客端与管理端执行类型检查、构建和 Lint。
- 为行程筛选、结构化回答解析、会话恢复和响应式关键逻辑增加测试。
- Java 后端执行服务层与控制器测试，覆盖鉴权、规划降级、反馈关联和指标聚合。
- AI 服务执行路由、结构化输出、超时与降级测试。

### 8.2 流程验收

1. 游客可从首页完成需求填写、获得路线、查看地图、进入数字人讲解并提交反馈。
2. 管理员修改首页、景点、路线或知识库后，游客端能看到正确结果。
3. 管理员能查看来自真实会话与反馈的运营指标。
4. AI 或地图服务失败时，系统给出可理解的降级结果和重试入口。
5. 游客端在五个目标宽度下无关键布局或操作故障。
6. 管理后台在平板与窄屏下仍可完成核心管理操作。
7. 仓库中不保留已知的模型配置 mock 操作或前端明文敏感密钥。

## 9. 非目标

- 本轮不替换 React、Spring Boot、FastAPI、Live2D、Qdrant 或现有地图供应商。
- 不开发原生 iOS 或 Android 应用；移动端通过响应式 Web 与可安装 Web 能力演进。
- 不承诺脱离真实模型与外部地图服务后的所有高级能力，但必须提供基础降级体验。
